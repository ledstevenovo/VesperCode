# VesperCode v2 Relaxed Identity Specification

> Version: `0.2.0-alpha`
> Status: implementation slice in progress
> Historical contract: [`SPEC_v1_frozen.md`](SPEC_v1_frozen.md)

## 0. Migration boundary

VesperCode v1 (`0.1.0`) is frozen. Its canonical JSON, SHA-256 identity
bindings, twelve-migration database, reference image evidence, release
records, and tests remain historical read-only material. V2 does not validate
or consume those v1 digests as authorization conditions.

V2 uses a fresh database file, `vespercode-v2.sqlite`, and a separate runtime
namespace. V1 and V2 databases, candidate trees, and evidence records are not
implicitly interoperable. A v1 database must never be upgraded in place by
the v2 initializer.

## 1. Problem and user stories

V1 made every internal identity a content-addressed security binding. That
provided strong integrity semantics, but made ordinary behavior changes,
testing, and recovery unnecessarily coupled to canonicalization and repeated
hash checks. V2 keeps behavior-based controls and makes references ordinary
opaque runtime IDs.

1. As a user, I can create a run with an opaque run ID and inspect its state
   without interpreting an ID as a proof about file contents.
2. As a user, I can let a Mock LLM propose an action and receive deterministic
   feedback when policy blocks it.
3. As a user, I can see a corrective action follow a blocked or failed action,
   while feedback stays scoped to the current run.
4. As a user, I can approve a writeback subject only while its candidate ID and
   candidate revision still match the current control-plane record.
5. As a user, I can run the public/demo composition without giving it formal
   workspace, shell, credential, Docker, or network capabilities.
6. As an operator, I can retain v1 release records for audit without making
   them a prerequisite of v2 startup.

## 2. Functional requirements

### FR-V2-IDENTITY

- Generate `RunId`, `CandidateId`, `ActionId`, `ApprovalId`, `DisclosureId`,
  `ArtifactId`, `TransactionId`, `SnapshotId`, and `SubjectId` as random UUID
  references.
- `CandidateIdentityV2` contains `candidate_id`, `snapshot_id`, and integer
  `revision`; it does not contain `candidate_digest`.
- `ActionInstanceV2` contains `action_id` and `action_type`; it does not
  contain semantic or instance digests.
- `FinalWritebackSubjectV2` contains `subject_id`, `candidate_id`, and
  `expires_at`; it does not contain `subject_digest`.
- IDs are lookup and log correlation keys only. They are not content
  authentication, authorization, or cross-machine integrity proofs.

### FR-V2-GOV

- Only recognized action families are accepted by the deterministic policy.
- All paths must be canonical relative paths, confined to the authorized
  workspace, and free of traversal, alternate separator, drive, and empty
  segments.
- Sensitive names and secret-like extensions are denied.
- Writes to tests, configuration, control-plane, delivery, gate, dependency,
  and other protected roots are denied. Protected files may still be read when
  a read action is explicitly allowed.
- No approval or model field can override a policy `DENY`.

### FR-V2-LOOP

- The harness owns context assembly, exactly one injected LLM call per turn,
  action parsing, dispatch, feedback recording, and stopping.
- Model-supplied `action_id` is rejected; IDs are generated by the harness.
- A blocked action produces structured feedback and does not write files.
- A later model action can correct the previous failure.
- The loop stops on `DONE` or a bounded turn budget and never auto-retries a
  completed turn.

### FR-V2-STORAGE

- The v2 SQLite schema is created independently of v1.
- Run lifecycle transitions use status/phase legality and optimistic revision
  compare-and-update.
- Candidate approvals consume once and additionally require the current
  candidate revision to equal the approval's recorded revision.
- Transactions are atomic; failed operations leave no partial approval state.
- Every table in the v2 schema (including `transaction_journal` and the
  `actions`, `disclosures`, and `artifacts` tables) has its required
  columns validated on open and on initialize; a malformed table under
  otherwise valid metadata is rejected fail-closed.

### FR-V2-WRITEBACK (Route A)

- Writeback to the real workspace is explicit only: a request must carry the
  run, candidate, candidate revision, a pending approval, and at least one
  `CREATE`/`REPLACE` operation with a canonical relative path.
- Validation is complete before any write: unknown candidate/run, stale
  revision, missing/consumed/mismatched approval, duplicate targets, policy
  denial, or CREATE/REPLACE target mismatch (including a missing parent
  directory) all return without a single workspace mutation and leave the
  approval untouched. The port exposes a non-mutating `validate` so target
  applicability is checked before the approval is consumed.
- Nothing that looks like a credential may enter the journal: a
  deterministic conservative content scanner
  (`governance/v2_secret_scanner.py`) checks the staged content of every
  operation and the observed original of every REPLACE target before the
  approval is consumed. A hit returns `DENIED` with zero writes, a PENDING
  approval, and no transaction; the refusal message and the scanner's
  marker ids never contain the matched secret material. The scanner is
  marker-based (assignment spellings, Bearer headers, PEM private-key
  headers, structured provider-token shapes), so it can refuse benign code
  that merely mentions credential handling (documented false positives)
  and it cannot catch unstructured random secrets (documented gap).
- Approval consumption, transaction creation, and journaling of intended
  writes (plus observed originals) happen in one SQLite transaction.
- Writes go through a real workspace port as ``PlannedWriteV2`` values: the
  content is written to a temporary file in the target directory, flushed and
  fsynced, the full boundary is rechecked, and CREATE publishes via link
  while REPLACE publishes via atomic replace. No directory is ever created
  implicitly.
- Publication is compare-and-publish: immediately before the atomic replace,
  a REPLACE must observe that the target still holds exactly the journaled
  original bytes (ordinary byte/text comparison, never a digest); an external
  modification between preflight and publication raises
  ``WorkspaceContentMismatchError``, performs zero unsafe overwrite, and
  leaves a durable ``UNRESOLVED`` transaction for recovery. CREATE stays
  no-clobber, so a target that appeared after preflight is never
  overwritten.
- Rollback restores publish through the same binding: undoing an applied
  REPLACE expects the applied bytes on disk and refuses an externally
  modified target instead of overwriting it.
- Durable states: `PREPARED -> WRITING -> COMMITTED`, with `UNRESOLVED` on a
  write fault and `ROLLED_BACK` available before terminal state. Terminal
  states are final and the state machine is enforced by the database.

### FR-V2-RECOVERY (Route A)

- Non-terminal transactions are discoverable from the database alone; no
  process memory is required.
- A byte-comparison preview classifies every journal row as `APPLIED`,
  `PENDING`, `DRIFTED`, or `UNREADABLE`.
- Apply completes pending writes and rolls the state to `COMMITTED`; rollback
  restores recorded originals (re-creating replaced content, removing created
  files) and records `ROLLED_BACK`.
- Rollback is content-bound in both directions: restoring a replaced file
  publishes through a planned write that expects the applied bytes, and
  removing a created file compares the current bytes to the journaled
  content immediately before the unlink, so externally changed content is
  refused (FAILED, non-terminal transaction) rather than overwritten or
  deleted. The port protocol exposes no unbound removal.
- A `DRIFTED` or `UNREADABLE` target blocks both apply and rollback
  fail-closed; recovery never guesses over externally modified bytes.
- A corrupted journal is rejected before any state advance: an active
  transaction with no journal rows, rows bound to a different transaction,
  positions that are not contiguous from zero, or malformed row shapes
  (unknown action types, wrong original-content shape) make
  preview/apply/rollback raise a closed failure that leaks no journal
  content, and the transaction is never advanced to `COMMITTED` or
  `ROLLED_BACK`.
- Ordinary file metadata and byte comparison are the only content checks;
  no content digest is used as identity or authorization.

### FR-V2-VALIDATION (Route B / B1)

- The v2 candidate control identity is a frozen record of an opaque
  `candidate_id`, an opaque `snapshot_id`, a non-negative `revision`, and a
  bounded `status` (`ACTIVE`/`SUPERSEDED`); it carries no content digest.
  Mutating staged content never regenerates an identity value — only the
  revision advances (`candidate/v2_candidate.py`).
- A candidate diff record associates one stored diff artifact with one
  candidate revision through ordinary `diff_id`/`artifact_id` references;
  no preimage/postimage digest enters the control plane.
- A reference profile record is keyed by `reference_profile_id` plus
  `profile_revision` and carries the declared tool metadata (Python,
  pytest, Ruff, Mypy versions) as plain configuration — no manifest
  digest and no gate-identity verification (`profiles/v2_reference.py`).
- Validation run/result records are keyed by `run_id`, `candidate_id`,
  `candidate_revision`, `reference_profile_id`, and
  `reference_profile_revision`, with a bounded status
  (`PENDING`/`PASSED`/`FAILED` for runs; terminal-only for results) and a
  bounded error message that is required exactly for `FAILED` and capped
  at 512 characters (`contracts/v2_validation.py`).
- Evidence acceptance is a pure fail-closed check,
  `verify_evidence_binding`: the result must belong to its validation run,
  the result and run must agree on all five keys, and the run must match
  the currently expected binding. Evidence from another candidate, run,
  or reference profile — or recorded against a stale revision — is
  rejected; a revision advance invalidates earlier references and new
  evidence must be recorded against the current revision.
- Strict exact-field mapping parsers reject unknown and missing fields, so
  v1-shaped digest payloads never parse as v2 records.
- The v3 schema stores the records durably: `reference_profiles` (the
  declared profile revisions, immutable per key),
  `candidate_diffs` (one authoritative diff per candidate revision), and
  `validation_runs` (the five-key binding with bounded status/error).
  Their columns are validated on open and initialize like every other v2
  table; no v1 row is migrated and a v1 database remains read-only
  legacy. Creation fails closed on cross-run candidates, foreign-run
  artifacts, stale candidate revisions, unknown reference profile
  revisions, and duplicate (profile id, revision) declarations; result
  recording is one-shot from `PENDING` with the same bounded status/error
  rules and is currency-checked in one transaction — the candidate must
  still belong to the validation run's run at the recorded revision and
  the referenced profile revision must still exist and revalidate as a
  record, otherwise the run stays `PENDING` and the call rejects
  fail-closed, so no terminal evidence is ever written for a stale or
  drifted binding.
- No new v2 module imports a v1 digest module for an identity or
  authorization decision; the v1 candidate/validation/reference modules
  remain untouched read-only legacy.

### FR-V2-DISCLOSURE (Route B / B2)

- A disclosure grant is a frozen record keyed by an opaque `grant_id`
  and by the `disclosure_id` of the approved subject it was created
  from (one grant per disclosure), plus the harness `run_id`, the bound
  `reference_profile_id`/`reference_profile_revision`, an ISO-8601
  `expires_at`, a bounded byte budget with a consumed total, the
  allowed source categories, and the allowed path scopes
  (`ROOT`/`FILE`/`DIRECTORY`); its closed status vocabulary is
  `PENDING`/`ACTIVE`/`REVOKED`/`EXPIRED`/`EXHAUSTED`
  (`governance/v2_disclosure.py`).
- A grant is created `PENDING` and requires an explicit user approval
  (`activate_disclosure_grant`) before it authorizes anything;
  activation is one-shot, revocation is terminal from `PENDING` or
  `ACTIVE`, and no content digest of the subject or any request is
  computed, stored, or consulted anywhere in the disclosure plane.
- A per-request disclosure authorization is keyed by its own opaque
  `authorization_id` plus the `grant_id`/`run_id`/`request_id`/
  `endpoint_id` control references, its requested sources (category
  and, for `FILE_CONTENT`, a canonical path), its bounded byte charge,
  and its one-shot `AUTHORIZED` → `CONSUMED` state.
- `authorize_disclosure_request` charges atomically in one SQLite
  transaction or not at all: it revalidates the grant (same run,
  `ACTIVE`, unexpired — a stale grant is flipped to `EXPIRED` and
  rejected in the same commit), the provider endpoint's reference
  profile id/revision against the grant's binding, the requested
  sources against the granted categories and path scopes (exact-file,
  segment-boundary directory, or root matching), and the cumulative
  byte budget before writing the authorization row, its source rows,
  and the grant's new consumed total (flipping to `EXHAUSTED` when the
  budget is fully consumed).  Every rejection — unknown grant, wrong
  run, `PENDING`/`REVOKED`/`EXPIRED`/`EXHAUSTED`, unknown endpoint,
  profile mismatch, out-of-scope sources, budget exceeded — leaves
  zero charge and zero authorization rows.
- An exact replay of an already-authorized request returns the
  original authorization with no second charge; the same request id
  with a different payload (run, endpoint, charge, or sources) is a
  replay conflict that changes nothing.
- Provider endpoints are declared as immutable records keyed by an
  opaque `endpoint_id`, carrying the provider name and the reference
  profile id/revision they serve (`profiles/v2_endpoints.py`); no
  endpoint record carries an address, a credential, or a digest.
- The provider call boundary (`providers/v2_call.py`) performs exactly
  one transport call per authorization: it re-checks the endpoint's
  existence and provider/profile binding, the authorization's
  grant/run/request/endpoint binding and `AUTHORIZED` state, and the
  grant's `ACTIVE` and unexpired status (early diagnostics), then
  delegates to the authoritative atomic consume
  (`consume_disclosure_authorization`): inside one SQLite transaction
  the binding, the `AUTHORIZED` status, the grant's `ACTIVE` state and
  its expiry as of an explicit deterministic consume-time clock, and
  the endpoint/profile binding are revalidated, and the one-shot
  `AUTHORIZED` → `CONSUMED` transition commits only if all of them
  hold — so a revocation or an expiry crossing between the reads and
  the consume rejects the call with zero transport calls and no burned
  authorization.  The consume commits before the transport call, so a
  duplicate call can never double-call the provider (a failed call
  burns its authorization — there is no refund).  A provider error is
  never retried automatically; any transport exception or non-success
  response maps to the closed `PROVIDER_CALL_FAILED` code with a
  static message, so no raw provider exception text can reach the
  outcome.
- The credential plane is an injectable port
  (`credentials/v2_port.py`): hidden input is wrapped in a
  non-comparable, non-serializable, redacted secret object whose only
  accessor, `reveal`, is capability-gated — it requires the exact
  reveal capability minted once by the port module, which no public
  API of the package exposes and which only the provider call boundary
  obtains through a module-private friend seam; a missing argument or
  any other value (including a fresh look-alike instance of the
  private capability class) is rejected, so ordinary direct use of a
  wrapper cannot obtain the raw secret.  `set`/`clear`/`status` never
  project the secret, its length, or any derivative (status is
  provider, configured flag, and update time only), and
  `get_for_call` is the only call-boundary projection.  The real OS
  credential integration is out of scope for B2; the deterministic
  in-memory provider is the shipped implementation of the port, and
  the request/response records never carry a credential value.
- Strict exact-field mapping parsers reject unknown and missing
  fields, so v1-shaped digest payloads (`subject_digest`,
  `request_digest`, `schema_version`) never parse as v2 records; the
  B2 modules import no v1 module and no `hashlib`.

### FR-V2-LOCALUI (Route B / B3)

The v2 local integration layer is standard-library only and v2-only:
no B3 module imports a v1 CLI, governance, or web authority module,
and no B3 surface derives digest identity or accepts a third-party
package dependency.

- **Local services shell** (`shell_v2.py`): one `V2LocalShell` composes
  a real `V2Harness` (control database under
  `<workspace>/.vespercode`) plus the B2 credential port, and exposes
  closed operations only: run start/stage, run projections, explicit
  revision-bound writeback approval and apply, durable recovery
  preview/apply, and the non-revealing credential/disclosure
  projections.  The shell's writeback path additionally denies the
  control-plane directory, so staged content can never replace the
  v2 control database or its journal even after an explicit approval.
  The agent loop runs only behind an injected LLM factory: with none
  composed, run start and writeback fail closed with
  `NO_LLM_BOUNDARY` (no real provider transport exists in this slice).
  Staged content is process-local by Route A's architecture, so the
  shell binds each run's writeback to the staged operations observed
  when that run was staged; a fresh process finds `NOTHING_STAGED`
  and must use durable recovery instead.
- **Closed v2 CLI** (`cli_v2.py`, console entry `vespercode-v2`): a
  closed argparse grammar — `run`, `status`, `writeback`, `recovery`,
  `credential-status`, `disclosure-status`, `serve` — where every
  argument is bounded and typed (existing workspace directory,
  bounded task text, bounded opaque identifiers, closed decimal
  counts/ports, literal loopback host), and no shell, argv
  passthrough, provider URL, secret, policy, or profile option
  exists.  Writeback and recovery are preview-by-default and require
  the explicit `--apply` switch; recovery `--apply` additionally
  requires an explicit `--transaction-id`.  Every projection is
  bounded and non-revealing; shell errors exit nonzero with the
  closed `error: <code>` line.  The legacy v1 `vespercode` console
  entry point remains untouched and is never imported by the v2 CLI.
- **Loopback WebUI security boundary** (`web/v2_security.py`): the
  closed security configuration binds `127.0.0.1` only with a
  validated port; bounded local sessions carry independent 256-bit
  tokens, a bounded time-to-live, and bounded concurrency (both
  injectable for deterministic tests); and one request authorizes
  through the manager-bound `authorize_v2_local_request` in the fixed
  order HOST -> SESSION -> ORIGIN -> CSRF (state changes only), first
  failure wins, with stable closed codes, statuses, and bounded
  payloads.  The SESSION check is self-contained in the boundary: the
  cookie value must resolve to a session registered in the given
  `V2LocalSessionManager` and still be live at the manager's clock, so
  a forged valid-looking session value or an expired one rejects with
  `SESSION_INVALID`/`SESSION_EXPIRED` before the Origin and CSRF
  checks and before any domain call, and an authorized result carries
  the resolved live session.  There is deliberately no session-taking
  authorization variant: a caller cannot pass an arbitrary session
  object, so no route handler can bypass the manager.  The CSRF token
  travels as the closed synchronizer form field so plain HTML pages
  (no client scripts) stay protected.  Every response carries the
  exact CSP (script-src never widened by the nonce path) plus nosniff,
  frame-deny, and no-referrer headers.
- **Typed form contracts** (`web/v2_forms.py`): every mutation and
  query endpoint accepts exactly one closed form — an exact field set
  with per-field typed parsers (bounded opaque identifiers, decimal
  revisions, bounded task text, the literal `CONFIRM`, the CSRF token
  form).  Unknown, missing, duplicated, or malformed fields reject
  with closed codes before any domain call; the URL-encoded body
  parser rejects duplicate fields (HTTP parameter pollution) and
  bounded-excessive field counts.  No form carries a filesystem path,
  a policy or profile override, a provider URL, a secret, or file
  content.
- **Framework-agnostic WebUI application** (`web/v2_app.py`): a
  closed route table (one GET/POST pair per control; anything else is
  a static 404/405 with security headers), the fixed security order
  before any form parsing or domain call, binding pre-checks that
  keep unknown, stale, or mismatched run/candidate/revision forms
  away from every mutation, all mutations requiring the explicit
  `CONFIRM` literal and the bound opaque IDs, HTML rendering that
  escapes every projected value, and pages that carry only bounded
  control-plane facts — never a secret, file content, or request
  body.  Safe GET reads establish a fresh session; state changes
  require an existing session, a loopback Origin matching the
  request's own Host, and the synchronizer token.
- **Standard-library loopback server** (`web/v2_server.py`): the
  launcher binds the literal loopback host only and validates the
  port before any socket opens; request bodies are bounded
  (64 KiB) and must carry the URL-encoded content type (415/413
  before parsing, with the rejected body drained bounded so the
  client can read the rejection); only GET and POST dispatch, other
  methods reject 405; duplicate query fields and parameter pollution
  reject; nothing about a request is logged; and responses are
  served single-threaded on the caller's thread (the composition
  shares one SQLite control connection, so the WebUI must be served
  by the thread that created its shell — the CLI `serve` command
  does exactly that).

### FR-V2-EXEC (Route B / B4a + B4b-01)

The v2 Docker validation/execution plane is standard-library only and
v2-only: no Route B execution-plane module imports a v1 Docker,
profile, or validation authority module (the pydantic-bound,
digest-pinned v1 execution modules remain read-only legacy) and no
module derives digest identity.  B4a ships the closed contracts, the
injectable binding/readiness/execution boundary, and the read-only
probe; B4b-01 adds the optional real container execution adapter behind
the same ports and the same B4a gates.

- **Execution profile record** (`execution/v2_profile.py`): one
  `ExecutionProfileRecordV2` keyed by an opaque
  `execution_profile_id` plus a non-negative revision and bound to an
  opaque reference profile id/revision (the B1 plane).  Every
  parameter is closed and fail-closed: an opaque local image token
  (never a URL, registry/repository/tag spelling, or 64-hex
  digest-shaped value), `network_disabled=True`, a non-root
  `uid:gid` (both ids >= 1), `read_only_rootfs=True`,
  `all_capabilities_dropped=True`, `docker_socket_mounted=False`,
  `workspace_mount_read_only=True`, and bounded `timeout_seconds`
  (1..600) and `max_output_bytes` (1..4 MiB) ceilings.  No registry
  credential field exists at all.
  `execution_profile_from_mapping` accepts an exact field set only —
  a v1 digest-shaped payload (gate digests, `schema_version`, nested
  `resources`/`environment` blocks) never parses as a v2 profile.
- **Execution request contract** (`execution/v2_execution.py`): one
  `ExecutionActionRequestV2` carries the control bindings — the
  request, the execution profile, and the reference profile (opaque
  ids plus revisions), the run/candidate it targets (the B1
  identity plane: `run_id`, an argv-token-conformant `candidate_id`,
  and the `candidate_revision` it cites), and the B1
  `validation_run_id` the production binding requires (`None` is
  the B4a isolated-fake spelling; the production database binding
  fails closed on an uncited request) — plus an `action_kind` from
  the closed vocabulary (`EXECUTION_ACTION_KINDS_V2`; B4a:
  `VALIDATE_CANDIDATE` only, with a per-kind grammar pinning the
  frozen argv executable token and the exact argument count).  For
  `VALIDATE_CANDIDATE` the two argv argument slots are bound to the
  request's own `candidate_id` and the decimal spelling of its
  `candidate_revision`, so the adapter-facing argv is a closed
  projection of the request's control fields and cannot drift from
  them; the validation citation is a control-plane key and is never
  projected into the argv; a shell command string, an option token,
  a path, a URL, or a digest-shaped token rejects at construction.
  The request schema has no image, URL, registry, credential,
  environment, command, or shell field at all.
- **Sanitized outcomes**: the executor-facing `ExecutionResultV2`
  (closed status, bounded exit code, sanity-bounded output) maps to
  the caller-facing `ExecutionOutcomeV2` — a closed status, a closed
  error code, the static message of that code, a bounded exit code,
  and an output excerpt capped at 2048 characters and stripped of
  control characters; the outcome record re-verifies its own closed
  shape at construction, so an unsanitized outcome cannot be
  represented.  Readiness verdicts (`ExecutionReadinessResultV2`)
  carry only a status and, when NOT_READY, one closed reason.
- **Injectable execution/readiness boundary**
  (`execution/v2_executor.py`): one `V2ExecutionService` over the
  bound profile, the injectable read-only control-plane binding lookup
  (`V2ExecutionBindingPort`: the cited run/candidate pair must
  resolve together and the cited candidate revision must be the
  candidate's CURRENT revision — the same B1 identity plane — and,
  for a request that cites one, the cited validation run must resolve
  as the terminal PASSED validation of that current revision under
  the request's own reference profile id/revision; the port returns
  one closed `ExecutionBindingOutcomeV2` whose kind is from the
  closed `EXECUTION_BINDING_OUTCOME_KINDS_V2` and the service
  re-verifies every field of the returned facts), an
  injectable `V2ReadinessPort`, and an injectable `V2ExecutionPort`.
  The order is fixed: a non-record request (for example a shell
  string) rejects outright; execution-profile and reference-profile
  id/revision mismatches reject before the binding lookup is even
  consulted; the production service STRUCTURALLY requires the
  request to cite a validation run — an uncited request rejects
  with the closed `VALIDATION_BINDING_REQUIRED` code before the
  binding port is even consulted, so the requirement does not depend
  on which binding port a caller injects (a production service over
  a permissive port still cannot execute an uncited request), and
  only `V2ExecutionTestService` — the explicitly test-only subclass,
  non-production by contract — relaxes exactly this one gate for the
  offline fakes; an unknown, foreign, or stale run/candidate binding
  or a missing, foreign, stale, profile-mismatched,
  corrupted, or non-PASSED cited validation rejects with a closed
  code BEFORE the readiness port is consulted and with zero executor
  calls; a NOT_READY verdict rejects before the executor is touched;
  execution is exactly one port call with no automatic retry; any
  executor exception or hostile return maps to the closed
  `EXECUTION_FAILED` outcome with a static message, so raw exception
  text never reaches an outcome.  `FakeV2BindingLookup`,
  `FakeV2Executor`, and `FakeV2Readiness` are the deterministic
  offline fakes — the whole boundary is testable without Docker, and
  the offline suite drives the production binding gate over a real
  v2 control database through the B4b-02A adapter below.
- **Production database-backed binding — B4b-02A**
  (`execution/v2_database_binding.py`):
  `DatabaseBackedExecutionBinding` implements
  `V2ExecutionBindingPort` over a real `V2Database`, read-only and
  fail-closed: the request must cite a validation run (an uncited
  request answers the closed `VALIDATION_REQUIRED` rejection —
  defense in depth with the production service's own structural
  citation gate, which rejects an uncited request before the port is
  even consulted); the
  cited run must exist and the cited candidate must exist, its row
  must revalidate as a B1 control identity, and it must belong to
  the cited run; the cited validation's row must revalidate as a B1
  `ValidationRunRecordV2` and bind the same run, the same candidate,
  at the CURRENT candidate revision, under the request's own
  reference profile id/revision; that profile revision row must
  still exist and revalidate; and the validation must be terminal
  `PASSED`.  Corrupted or missing rows answer the corresponding
  closed NOT_FOUND kinds — never fake facts — and the lookup never
  writes (no approval consumption, no validation result creation,
  no candidate advancement) and holds no cached state, so a freshly
  reopened database in a fresh process resolves the same committed
  binding.  Record-shape failures are closed rejections;
  infrastructure failures beyond record shape propagate loudly and
  still execute nothing.  No shell, network, Docker, or subprocess
  behavior is added by this adapter.
- **Optional read-only Docker probe**
  (`execution/v2_docker_probe.py`): the clearly separated, read-only
  subprocess edge of the slice — a read-only readiness probe over the
  operator's docker CLI (`docker image inspect <token>`, then
  `docker info` only to distinguish a missing image from an
  unreachable daemon).  Closed literal argv with `shell=False`, a
  bounded 15-second timeout, all command output discarded (no digest
  is ever parsed — there is no v2 digest authorization), and an
  injectable command runner so every probe decision is covered by
  offline tests; the v2 unit job never exercises the real subprocess
  edge, and no container is ever created, run, pulled, or pushed.
- **Optional real container execution adapter — B4b-01**
  (`execution/v2_docker_executor.py`): `SubprocessDockerExecutorV2`
  implements `V2ExecutionPort` behind the same B4a
  binding/readiness/approval gates — real execution is opt-in through
  this one adapter and cannot be reached any other way.  It accepts
  only the closed `ExecutionActionRequestV2` plus
  `ExecutionProfileRecordV2` (never a shell string, never arbitrary
  argv — the request grammar already pins the frozen argv) and drives
  one closed command sequence per run through an injectable command
  runner: `docker create --pull never` with the closed isolation flag
  set (network `none`, the profile's non-root uid:gid, read-only
  rootfs, `--cap-drop ALL`, frozen memory/memory-swap/pids/cpu bounds,
  a bounded `/tmp` tmpfs, exactly one READ-ONLY bind of the
  operator-configured workspace at `/workspace` — no host string, no
  environment, no entrypoint override, no volume flag, no docker
  socket, no registry credential anywhere in the argv; the profile
  record represents only timeout and output bounds, so the adapter
  freezes the rest); `docker inspect` re-verifies the daemon-side
  configuration of the exact created container (network mode,
  read-only rootfs, cap drop, privileged, memory/swap/cpu/pids
  limits, tmpfs, non-root user, image reference, the exact command,
  and the exact read-only workspace bind) BEFORE it starts, and any
  drift fails closed with nothing run; `docker start --attach` is
  the single attached run, bounded by the profile's
  `timeout_seconds` (one monotonic deadline covers create, inspect,
  and start) and by the profile's byte cap over collected stdout and
  stderr — an output overflow fails closed, never silently truncating
  an otherwise accepted run; a timeout kills the attach process and
  `docker stop --time 0` stops the exact container; and
  `docker rm --force` removes the exact container after every create
  that succeeded, best-effort and never able to change the already
  determined result.  Every phase failure — runner exception, hostile
  runner return, timed-out create/inspect, exhausted time budget —
  maps to the closed `FAILED` result with empty output, so no
  CLI/daemon error text, raw command, or secret can enter
  `ExecutionResultV2` (the service then sanitizes even that into the
  caller-facing outcome); no retry exists anywhere.  The default
  bounded subprocess runner exists only for opt-in operator-driven
  execution; the v2 unit job never exercises it (the offline suite
  proves every decision with a scripted fake runner), and the optional
  real-Docker integration module skips honestly when the CLI, the
  daemon, or a token-named local image is unavailable.

## 3. Non-functional requirements

- **NFR-V2-BOUNDARY:** no arbitrary shell, executable, user-provided argv,
  Docker socket, or unrestricted network capability is introduced by v2.
- **NFR-V2-DETERMINISM:** core behavior is offline-testable with an injected
  Mock LLM and in-memory workspace port.
- **NFR-V2-PRIVACY:** credentials never enter IDs, SQLite rows, feedback,
  reports, or logs.
- **NFR-V2-RECOVERY:** writeback remains explicit, one-shot, revision-bound,
  and reports unresolved state rather than guessing after a fault.
- **NFR-V2-COMPATIBILITY:** v1 files and published evidence remain unchanged
  historical artifacts; no v2 path reads their digest fields as permissions.
- **NFR-V2-DELIVERY:** CI runs one documented unit-test command on every push,
  including the v2 offline suite.

The initial SQLite tables are `runs`, `snapshots`, `candidates`, `actions`,
`disclosures`, `artifacts`, `writeback_approvals`, and `transactions`, plus a
small `v2_schema_meta` table and (from schema v3) `transaction_journal`,
which stores each intended write with its observed original for recovery.
Route B1 adds three more v3-schema tables: `reference_profiles` (declared
reference profile revisions keyed by `reference_profile_id` +
`profile_revision`), `candidate_diffs` (one authoritative diff artifact
reference per candidate revision), and `validation_runs` (validation runs
keyed by run, candidate, candidate revision, and reference profile
id/revision, with a bounded status and error). Route B2 adds six more
v3-schema tables: `provider_endpoints` (declared endpoints keyed by an
opaque `endpoint_id` with their provider and reference profile binding),
`disclosure_grants` (one grant per approved disclosure subject, keyed by
`grant_id`, with the run, profile binding, expiry, byte budget, consumed
total, and closed status), `disclosure_grant_categories`/
`disclosure_grant_scopes` (the granted category and path-scope children),
`disclosure_authorizations` (per-request authorizations keyed by
`authorization_id` and unique per `(grant_id, request_id)`, with the
run/endpoint references, charge, and one-shot consumed state), and
`disclosure_authorization_sources` (the requested source children). All v3
tables — Route A's included — are validated column-by-column on open and
initialize.
IDs are ordinary primary/foreign keys. Candidate change detection uses
`revision` and `updated_at`; no content digest is required for an
authorization decision. Staged loop content lives only in the in-memory
staging port; it becomes durable at writeback begin time, inside the
journal, after the approval is consumed.
Route B3 adds **no new tables and no schema version change**: the local
integration layer reads and writes the existing v3 tables through the
same fail-closed `V2Database`, extended only with two bounded read
projections (`list_runs`, `list_disclosure_grants`; fail-closed
1..500 limits) used by the shell's status and disclosure summaries.
Route B4a adds **no new tables and no schema change** either: the
execution plane is contract modules plus injectable ports with no
database wiring yet — a later slice wires profile persistence and
validation-execution recording into the same fail-closed `V2Database`.
Route B4b-01 (the real container execution adapter) adds **no new
tables and no schema change** as well: the adapter is an execution-
edge module behind the existing ports, so the same future wiring
covers it.

## 4.1 Technology choices

The v2 alpha deliberately uses Python's standard library for UUID generation,
dataclasses, SQLite, `unittest`, and the injected Mock boundary. This keeps
the core mechanism runnable without network access or dependency installation.
The existing Pydantic/FastAPI/Docker components remain available to later v2
integration slices, but they are not imported by the current v2 identity,
policy, database, memory, or loop modules.

## 5. Credential threat model and distribution

V2 never accepts credential values in action payloads, IDs, memory, SQLite, or
the Mock adapter. The Route B2 credential port (`credentials/v2_port.py`) makes
that boundary explicit and injectable: hidden input is wrapped in a redacted,
non-comparable, non-serializable secret object; only the provider call
boundary consumes `reveal`, and only between its own frame and the single
transport edge; the status projection carries no value, length, or derivative;
and no v2 table has a column that could accept a credential.

**B4b-02C1 adds the production OS-backed implementation behind the same
port** (`credentials/v2_os_store.py`): `OSV2CredentialProvider` over an
injectable OS backend whose real implementation is the Windows Credential
Manager backend (lazy, function-local `win32cred`/`pywintypes` imports — the
module and the wheel stay standard-library only, and a host without pywin32
fails closed with `CREDENTIAL_BACKEND_UNAVAILABLE`). Every operation first
proves the backend (identity in the closed `WINDOWS_CREDENTIAL_MANAGER` set
plus a real write/read/delete capability cycle of the backend's own
`vespercode/v2/probe` target); `set` extracts the raw value only through the
storage-reveal capability minted by the port module for exactly this adapter,
writes it under `vespercode/v2/credential/<provider>` (a namespace disjoint
from the probe target and from every v1 `vespercode/v1/` target), re-verifies
the backend after the write, and retains nothing; `get_for_call` re-probes and
reads fresh (no cache); `status` reads metadata only (the stored value is
never decoded on the status path); `clear` deletes idempotently. An unsafe,
unavailable, malformed, or identity-mismatched backend or entry fails closed
with the static closed `V2OSCredentialStoreError` — never a fallback backend
and never the secret. The v1 credential service is not the v2 authority and
is never imported. The raw value of a secret exists in exactly two
capability-gated frames — the OS-store write frame (`reveal_for_storage`,
granted only to the OS adapter) and the one provider transport call frame
(`reveal`, granted only to the provider call boundary); the two capabilities
are minted separately, handed only through module-private friend seams, are
absent from every public API, and are never interchangeable.

**B4b-02C1 also adds the real provider transport adapter behind the B2
transport protocol** (`providers/v2_transport.py`):
`V2ProviderTransportAdapter` is constructed from one v2 endpoint record and
the reference profile record it must bind (never a URL, `base_url`, header
set, argv, or shell input); the sole trusted destination derives from the
closed built-in provider address map (`OPENAI` →
`https://api.openai.com:443/v1/chat/completions`), and an endpoint for an
undeclared provider cannot even construct the adapter. The request body is
the bounded deterministic control-plane projection of the call request
(control IDs and revisions only); the closed read timeout, the closed
request-body bound, and the closed response-body bound are enforced; exactly
one HTTP edge call happens per `call` with no retry and no redirect follow;
and every edge exception, non-success status, non-conforming result, or
over-bound body maps to the closed `FAILED` response — the response body and
the credential never appear in any response, outcome, record, or retained
state. The real `httpx` edge is the only network edge of the v2 provider
plane and imports httpx lazily inside the call; the offline unit suite never
makes a real network call (it exercises the adapter through injectable fake
edges), and the real edge is not exercised by any recorded run.

The shipped default port implementation of the local shell and CLI remains
the deterministic in-memory fake (the OS-backed provider is an injectable
production adapter, not a wired caller); no real network call exists in the
offline unit suite, and the provider call service is still not composed into
the loop, CLI, or WebUI.

The historical v1 wheel and reference image remain available as v1 release
evidence. The v2 alpha package declares version `0.2.0a0`; its database path
and behavior contracts are independent of v1 artifacts. The distribution now
exposes two console entry points: the legacy `vespercode` script still targets
the frozen v1 CLI (a read-only compatibility surface that v2 never imports),
and the new `vespercode-v2` script targets the closed v2 local CLI
(`vespercode.cli_v2:main`).  Route B4a added the Docker validation
execution profile and the injectable execution/readiness boundary
(profile, contracts, service, deterministic fakes, and an optional
read-only readiness probe), Route B4b-01 added the optional real
container execution adapter behind the same ports, and B4b-02A added
the production read-only database-backed binding (still unwired into
any caller).  **B4b-02B release automation** is now a separate,
independent, manually dispatched workflow
(`.github/workflows/release-v2-alpha.yml`): it verifies the `0.2.0a0`
identity, runs the documented offline v2 unit suite, builds the wheel
with the locked build toolchain, smoke-installs it through
`vespercode-v2 --help`, and uploads the wheel plus its adjacent
`<wheel>.whl.sha256` evidence as one CI artifact.  It creates no
GitHub Release object, pushes no registry image, performs no public
deployment, references no secret, and holds no write permission; the
frozen v1 protected release workflow
(`.github/workflows/release.yml`) stays byte-unchanged, pinned to
`v0.1.0`, and carries no v2 identity.  **B4b-02C public deployment
remains not started** (C1 — the OS credential adapter and the real
provider transport boundary — is complete; C2 — any non-loopback
binding, TLS, or remote operator surface — is not started).

The v2 source surface is packaging-guarded: every v2 production module
(the `v2*.py` modules — including, from Route B4, the five
`execution/v2_*.py` modules — plus `governance/relaxed_policy.py`,
`runtime_v2.py`, and — from Route B3 — `shell_v2.py` and `cli_v2.py`)
must appear in the wheel package contract
(`REQUIRED_RUNTIME_MEMBERS` in `tests/smoke/package/test_wheel_contents.py`)
and in the Hatchling wheel selection (`packages = ["src/vespercode"]` with
the `vespercode/**/*.py` include). The offline guard
`tests/unit/v2/test_v2_wheel_contract.py` enforces both statically in the
ordinary v2 unit job on every push, so a v2 module cannot silently drop
out of the built wheel while source tests stay green. The real-wheel smoke
suite (build + install + member verification) is a separate
pytest/pipx-gated environment and is not run or claimed by the offline
unit job.

## 6. Acceptance criteria

- `tests/unit/v2` passes offline with Python standard library only.
- A generated ID is random-looking, opaque, and not a digest field.
- A v1-shaped database is refused by the v2 initializer.
- Out-of-workspace, traversal, sensitive, protected, and noncanonical writes
  are denied; safe `src/**` writes are allowed.
- A scripted dangerous action is blocked, feedback is stored, and a following
  corrective action succeeds.
- Memory from another run is never projected into the current run.
- Model-supplied action IDs are rejected.
- DONE succeeds; a bounded invalid loop stops at `MAX_TURNS`.
- A consumed approval cannot be reused, and a stale candidate revision cannot
  consume a pending approval.
- V1 release evidence is not modified by v2 implementation.

### Route A acceptance criteria

- A writeback with a valid pending approval commits: the real workspace file
  exists with the exact staged bytes, the transaction is `COMMITTED`, and the
  approval is `CONSUMED`.
- Stale, denied, mismatched, and duplicate-target requests perform zero
  workspace writes and consume no approval.
- A fault mid-apply marks the transaction `UNRESOLVED`; a fresh process over
  the same database previews it and either applies or rolls it back.
- Drift (a target matching neither the journal nor its recorded original) or
  an unreadable target blocks recovery fail-closed.
- Symlinked or junctioned path components are refused for reads, writes, and
  rechecks, including Windows reparse points that `Path.is_symlink` does not
  report.
- CREATE never clobbers an existing file and never implicitly creates a
  directory; REPLACE only overwrites an existing regular file.

### Route B1 acceptance criteria (candidate/validation/reference identity)

- A candidate control identity or diff record with an unknown status, a
  negative or boolean revision, an empty/whitespace/oversized identifier,
  or a non-string field rejects at construction.
- Advancing a candidate revision keeps the candidate and snapshot IDs
  unchanged (no identity regeneration), and previously recorded validation
  references bound to the old revision are rejected as stale.
- Validation evidence whose run, candidate, revision, or reference profile
  differs from the currently expected binding is rejected, as is a result
  that belongs to another validation run or that disagrees with its own
  run's keys.
- Strict mapping parsers reject unknown and missing fields, including
  v1-shaped digest payloads; no v1 module is imported by the B1 modules.
- The v2 initializer creates `reference_profiles`, `candidate_diffs`, and
  `validation_runs` in the v3 schema; malformed variants of those tables
  are rejected on open and initialize, and no v1 row is migrated.
- Cross-run candidates, foreign-run artifacts, stale candidate revisions,
  unknown reference profile revisions, and duplicate profile or diff
  revisions reject at creation time; a validation result completes a
  PENDING run exactly once with a bounded status and error, and only
  while the candidate still belongs to the same run at the recorded
  revision and the referenced profile revision still exists and
  revalidates — otherwise the run stays PENDING and no terminal evidence
  is written.
- All Route A transaction, writeback, and recovery tests keep passing
  unchanged.

### Route B2 acceptance criteria (disclosure/provider/credentials)

- A grant or authorization record with an unknown status, an
  out-of-range charge or budget, an invalid category, a
  mixed-`ROOT`/duplicate scope sequence, a non-canonical path, or an
  unparseable expiry rejects at construction; strict mapping parsers
  reject unknown and missing fields, including v1-shaped digest
  payloads.
- A `PENDING` grant authorizes nothing until the explicit user
  approval activates it; a second activation returns `False`.
- `REVOKED`, `EXPIRED` (including lazily flipped stale grants), and
  `EXHAUSTED` grants reject authorization with zero charge and zero
  authorization rows; a cross-run request rejects with zero charge.
- An authorization against an endpoint whose reference profile
  id/revision differs from the grant's binding rejects with zero
  charge (control IDs and revisions, never digests).
- The cumulative byte budget check, the replay check, the source
  scope check, and the authorization insert commit atomically: a
  request that loses the budget race leaves the consumed total and
  the authorization rows untouched, and a fully consumed budget
  flips the grant to `EXHAUSTED` in the same commit.
- An exact replay returns the original authorization with no second
  charge; the same request id with a different payload is a conflict
  that changes nothing.
- The authorization consume is one-shot and bound to its
  grant/run/request keys; a second consumer loses, and the consume is
  the authoritative gate: inside one transaction it revalidates the
  full binding, the `AUTHORIZED` status, the grant's `ACTIVE` and
  unexpired state as of the explicit consume-time clock, and the
  endpoint/profile binding — a revocation or an expiry crossing
  between an earlier read and the consume rejects with zero transport
  calls and no burned authorization, corrupted control rows reject
  fail-closed, and consumed authorizations are never refunded after a
  provider failure.
- A provider call performs exactly one transport call per
  authorization; every binding mismatch, missing credential, and
  not-active grant rejects before the transport is touched, a
  duplicate call cannot double-call the provider (the authorization
  is consumed before the transport call), and a transport exception
  or failure response produces the closed `PROVIDER_CALL_FAILED`
  code with the static message — never the raw exception, and never
  a secret in any outcome, record, exception, or database row.
- The credential secret wrapper is redacted, non-comparable, and
  non-serializable; `reveal` requires the exact reveal capability
  minted by the port module — no public API of the package exposes
  it, a missing or wrong argument rejects with the closed
  `CREDENTIAL_REVEAL_FORBIDDEN` error, and even a fresh instance of
  the private capability class does not unlock a secret; status
  projections carry only the provider, the configured flag, and the
  update time.
- The OS-backed credential adapter (B4b-02C1) fails closed on every
  operation: an unavailable backend (wrong platform, missing pywin32)
  and an unsafe backend (unknown backend identity, a failed
  write/read/delete probe cycle) raise the closed static store error
  on `set`/`get_for_call`/`status`/`clear` — never a fallback
  backend, never the secret, never a length or derivative; the module
  imports platform libraries only lazily inside functions, so it
  loads on any host; every operation probes the backend first, `set`
  re-verifies after the write, `get_for_call` reads fresh with no
  cache, `status` reads metadata only (the stored value is never
  decoded on the status path), `clear` is idempotent, the credential
  target namespace (`vespercode/v2/credential/<provider>`) is
  disjoint from the probe target (`vespercode/v2/probe`), and a
  malformed or identity-mismatched stored entry is a closed store
  failure — a foreign entry is never read as ours.
- The storage reveal seam (B4b-02C1) keeps the raw value in exactly
  two capability-gated frames: `reveal_for_storage` requires the
  storage capability minted for exactly the OS adapter, the
  provider-call reveal capability never unlocks it (and the storage
  capability never unlocks `reveal`), fresh look-alike instances of
  the private classes never unlock either, and neither capability
  appears on any public API.
- The real provider transport adapter (B4b-02C1) accepts only one v2
  endpoint record, the reference profile record it must bind, and an
  injectable HTTP edge — there is no URL, `base_url`, header, argv,
  or shell parameter; an endpoint/profile binding mismatch and an
  endpoint for an undeclared provider reject at construction; the
  URL derives only from the closed built-in address map; the request
  body is the deterministic bounded control projection (control IDs
  and revisions only), an oversized projection fails before the edge
  is touched, exactly one edge call happens per call with the closed
  timeout, no redirect is followed and no request is ever re-sent,
  every non-success status, non-conforming result, over-bound body,
  and every edge exception (including timeouts) map to the closed
  `FAILED` response, and the response body and the credential never
  appear in any response, retained state, or exception.
- The composed provider boundary (B4b-02C1) keeps the B2 call order:
  a credential-port infrastructure failure happens strictly before
  the atomic consume (nothing is burned, no transport is touched) and
  propagates loudly with the static closed message; a transport
  failure happens strictly after it (the authorization stays
  consumed — no refund), performs exactly one edge call, and the
  secret never enters any outcome or any byte of the control
  database; the adapter's independent binding recheck rejects a
  request that drifts past the service gate with zero edge calls.
- The real OS backend is exercised only by the opt-in Windows
  integration suite (`tests/integration/windows/`), which skips
  honestly when Windows, pywin32, or the operator opt-in
  (`VESPERCODE_V2_WINCRED_INTEGRATION=1`) is missing, refuses to
  clobber unknown entries, deletes what it creates, and proves zero
  `vespercode/v2/` residue; the offline unit suite runs the adapter

## 7. Risks and known limits

- Removing digest gates reduces content-authentication strength. V2 must not
  claim equivalent integrity guarantees; revision checks are control-plane
  freshness checks only.
- Real writeback (Route A) is journal-based: a crash between the temporary
  file write and the atomic publish can leave an orphaned
  `.vespercode-v2-*.tmp` file inside the workspace; the durable journal still
  drives recovery. Win32 offers no directory fsync, so a power loss after a
  `COMMITTED` state but before directory metadata flush could theoretically
  lose the rename; POSIX fsyncs the parent directory. These are documented
  residual windows, not claims of transactional filesystem guarantees.
- The compare-and-publish guard verifies the expected original bytes
  immediately before the atomic replace; a modification landing in the
  micro-window between that comparison and the rename could still be
  overwritten, because neither Win32 nor POSIX offers an atomic
  compare-and-rename for file content. This residual TOCTOU window is
  minimized (the comparison is the last operation before publication) and
  recovery drift detection still fails closed after any such event.
  The comparison itself uses decoded UTF-8 text, so a target that is not
  valid UTF-8 is refused rather than compared.
- The writeback journal stores staged file content in the local v2 control
  database because recovery requires it; the policy denies sensitive paths
  (`.env`, `.pem`, `.key`, ...) before journaling, and a deterministic
  conservative marker scanner refuses secret-like content (and the
  observed originals of REPLACE targets) before the approval is consumed.
  The scanner is marker-based, so it can refuse benign code that merely
  mentions credential handling (documented false positive) and cannot
  catch an unstructured random secret with no recognizable marker
  (documented gap); nothing in this line treats those bytes as identity
  or authorization.
- Real-provider disclosure, Docker validation execution, WebUI/CLI
  integration, and release automation remain Route B work; Route B1 has
  only delivered the identity/record contracts and their v3 storage —
  no validation execution exists yet, so a PASSED validation run is a
  control-plane fact recorded by a caller, not an executed check.
- Route B2 delivered the disclosure/provider/credential control plane;
  B4b-02C1 adds the production OS-backed credential adapter and the
  real provider transport adapter as injectable implementations behind
  the existing ports — but neither is wired into the harness loop, the
  CLI, or the WebUI (the shipped default remains the deterministic
  in-memory fake), the real HTTP edge is never exercised by any
  recorded run, and the real OS backend is exercised only by the
  opt-in Windows integration suite. A successful composed provider
  call proves the control plane permitted it and the transport
  boundary executed; no recorded run has contacted a real provider.
- The v2 OS credential adapter requires optional platform libraries
  (pywin32 on Windows) that the standard-library-only v2 wheel does
  not carry: a host without them fails closed with the closed
  `CREDENTIAL_BACKEND_UNAVAILABLE` error — no fallback, no file
  store, no environment import. The v2 backend proves Windows
  Credential Manager identity by platform, import, and a real
  write/read/delete probe cycle (the v1 store additionally verified
  the keyring backend object; the v2 adapter talks to the same Win32
  Credential API directly, deliberately without a keyring dependency
  — a documented, reasoned deviation from the v1 pattern).
- The real transport adapter's request body is the bounded
  control-plane projection of the call request (control IDs and
  revisions only): the authorized-content payload for real
  completions is deliberately a later slice, so this boundary proves
  the transport mechanism (destination derivation, timeout, bounds,
  redaction, one-call semantics) without claiming content-bearing
  provider calls exist yet.
- The transport read timeout is enforced by the HTTP edge (httpx) as
  passed by the adapter: a non-cooperating injected edge could ignore
  it, because Python cannot kill a blocked call from outside — the
  edge is a trusted seam, and the offline tests pin that the adapter
  always passes the closed timeout value to it.
- The closed provider address map is keyed by provider name: every
  endpoint record whose provider is `OPENAI` resolves to the sole
  trusted `api.openai.com` destination regardless of the endpoint
  id's intent. An unknown provider cannot even construct the adapter,
  but operator-declared endpoint records must be deliberate.
- The real OS backend decodes the Win32 UTF-16-LE credential blob
  exactly as it wrote it and converts the entry's `LastWritten` time
  for the status projection; a malformed blob, a wrong username, or a
  missing mandatory field is a closed store failure, and a stored
  entry written by any other tool under the v2 target namespace is
  never read as ours.
- The provider call boundary burns its authorization before the
  transport call (one-shot, no-refund), so a transport failure leaves
  the charge consumed and a retry requires a fresh authorization; this
  is deliberate — it makes double-calling the provider impossible —
  but operators must expect a failed call to spend budget.
- Disclosure scope matching is lexical (canonical relative paths
  compared as strings): `FILE` matches the exact spelling,
  `DIRECTORY` matches the directory and true descendants, and `ROOT`
  matches any path; two different spellings of the same file (for
  example after a case change on a case-insensitive host) are
  different paths to this plane.  The byte charge is caller-declared
  and bounded, not measured from payload bytes.
- Adding the B2 tables to the v3 schema (same in-place decision as
  B1) means a database created before B2 is rejected fail-closed by
  the strict table-set/column validation; it is never migrated in
  place, and a fresh v2 database path is required.
- The reveal capabilities (the provider-call reveal and the
  B4b-02C1 storage reveal) are enforced by object identity and naming
  convention, not cryptography: Python cannot forbid importing a
  module-private name, so the guarantee is that no public API of the
  package hands out either capability and every ordinary direct use of
  ``reveal`` or ``reveal_for_storage`` is rejected — a caller that
  deliberately imports a private friend seam (or reaches into the
  wrapper's private slot) is outside the public surface the boundary
  promises to protect.  Both seams are greppable, pinned by tests, and
  documented as single-consumer (the provider call boundary and the OS
  credential adapter respectively).
- The provider call boundary revalidates the grant state at consume
  time inside one transaction, so a revocation or expiry crossing
  between the reads and the consume rejects the call; the residual
  window is only after the consume commits (the authorization is
  burned and exactly one transport call happens — deliberate
  one-shot semantics, not a revalidation gap).
- Route B1 validation semantics are control-plane only: the five-key
  binding proves which candidate revision a run recorded, not that bytes
  are unchanged across processes or machines. Terminal outcomes are
  written only while the recorded binding is still current (candidate
  revision and referenced profile revision); a drifted run stays PENDING
  rather than terminalizing misleading evidence. The bounded error
  message is the only diagnostic retained; it is harness-written and
  length-capped, and it never authenticates content.
- Adding the B1 tables to the v3 schema (instead of a new schema version,
  per the Route B1 instruction) means a database created before B1 is
  rejected fail-closed by the strict table-set/column validation; it is
  never migrated in place, and a fresh v2 database path is required.
- Windows 8.3 short-name aliasing is resolved through full path resolution
  and component walks; reserved device names and trailing dot/space
  components are refused only on Windows hosts.
- V1 modules still contain digest terminology because they are preserved
  legacy code. New v2 modules must not import them for identity decisions.
- Symlink creation needs a privileged Windows environment; junction tests
  cover the reparse-point logic on ordinary Windows hosts, and the symlink
  test skips where creation is unavailable.
- Route B3 risks (local CLI/WebUI): staged content is process-local by
  Route A's architecture, so the shell binds each run's writeback to the
  staged operations observed when that run was staged — a fresh process
  cannot apply a previous process's staging (`NOTHING_STAGED`) and must
  use durable recovery; the WebUI session store is in-memory with a
  bounded count, so restarting the serve process logs every browser out
  (safe reads re-establish sessions automatically); the CSRF
  synchronizer token is a hidden form field, so the WebUI needs no client
  scripts but the token is bound to a session's lifetime only; the WebUI
  task bound is 4096 characters (the CLI takes the same bound), so longer
  tasks are rejected rather than silently truncated; the serve
  composition shares one SQLite control connection with its shell, so the
  WebUI must be served by the thread that created its shell (the CLI
  `serve` command does; an embedding that serves from another thread
  fails loudly with SQLite's thread check rather than silently
  cross-threading); the 413/415 rejections drain the rejected body
  bounded (16 MiB cap) so ordinary over-post clients can read the
  rejection, but a body beyond the cap is abandoned and the connection
  simply closes after the rejection.  The manager-bound request
  authorization proves the session is registered and live in the
  session manager it is handed (type-checked to be a
  `V2LocalSessionManager`; the app hands its own) — it cannot know
  about a process-global "one true manager", so any in-process code
  that constructs its own manager could authorize against that
  manager's own sessions; this is a same-process trust boundary, not a
  remote one.  The B3 surfaces carry no authentication beyond the
  loopback, session, origin, and CSRF gates: they are a local
  single-user tool, and any process on the same machine that can reach
  the loopback port can talk to the WebUI.
- Route B4 risks (execution profile and boundary): the execution
  profile is configuration identity, not an authorization gate — it
  cannot prove the image bytes match a pinned reference (the v1 digest
  chain is deliberately gone), so a profile revision only declares
  which configuration the operator bound.  The execution request binds
  the B1 control plane (run, candidate, current revision) through an
  injectable read-only lookup: B4a shipped the deterministic fake plus
  a test-local adapter, and B4b-02A shipped the production read-only
  database-backed binding (`DatabaseBackedExecutionBinding`) whose
  service gate also requires a cited terminal-PASSED validation run —
  but the adapter remains UNWIRED into any caller (no harness, CLI,
  or WebUI composes it), and the binding is check-time only (a
  candidate can still advance between the binding lookup and a real
  run until a one-shot consume exists).  The readiness probe
  resolves the opaque image token verbatim against the local daemon,
  so on hosts whose images exist only under registry/tag spellings
  (the closed token charset excludes `:` and `/`) readiness honestly
  answers IMAGE_NOT_AVAILABLE even though a tagged image is present —
  the real execution adapter accepts only the same token spelling, so
  an operator must maintain a token-named local image (for example
  `docker tag <image> vespercode-validation-image`) and any broader
  token-to-reference mapping remains B4b work.  The real execution
  adapter (B4b-01) isolates per run but is not a content guarantee: the
  daemon-side drift verification proves the daemon recorded the exact
  closed configuration of the created container, not that the image
  bytes match any external reference; a workspace directory with a
  comma cannot be mounted (the `--mount` value is comma-delimited);
  the default bounded subprocess runner kills the CLI process on
  timeout, but the CLI's own teardown of the attach stream is the
  daemon's behavior, so the exact-container stop (`docker stop --time
  0`) is the authoritative timeout enforcement; and a failed cleanup
  removal cannot change the already determined result — the closed
  result cannot carry cleanup status, so a daemon that refuses the
  removal can leave a stopped container that the operator must remove
  by hand.  The two subprocess edges — the read-only probe and the
  real execution adapter — both run the operator's docker CLI with a
  closed literal argv and bounded timeouts, and neither is ever
  exercised by the offline unit job (the command runner is
  injectable).  The execution plane still has no harness/CLI
  composition and no persistence of its own: profile persistence and
  validation-execution recording remain future wiring.
  B4b-02B ships the v2 alpha release path as a manual, read-only,
  source-artifact workflow only (see the release-path risks below).
  B4b-02C1 adds the production OS credential adapter and the real
  provider transport adapter as injectable, offline-testable
  implementations behind the existing B2 ports (the two real edges —
  the Windows Credential Manager backend and the httpx HTTP edge —
  are optional, lazy, and never exercised by the offline unit job);
  B4b-02C2 — public deployment (any non-loopback binding, TLS, or
  remote operator surface) — remains **not started**; Route B is not
  fully complete.
- Route B4b-02B risks (the v2 alpha release path): the produced alpha
  artifact is a workflow artifact, not a distribution channel — nothing
  is published, availability is transient (30-day retention), and the
  alpha is still installed from source for evaluation; the frozen v1
  release workflow triggers on every pushed "v*" tag and fails closed
  on its own frozen v1 admission pins (tag name, source commit, and
  package version), so pushing a v2 alpha tag would start that
  workflow to no effect — the v2 alpha path is workflow_dispatch-only
  and binds to the checked-out source commit instead of a tag; and
  the real wheel build/install proof (the release workflow's smoke and
  the pytest/pipx package smoke suite) runs only in its dedicated gated
  environments and is never claimed by the offline unit job, whose
  static contract parses the workflow files without executing them.

## 8. Coding Agent Harness domain and mechanism design

V2 retains the course-required Harness boundary: a self-owned loop, low-level
injectable LLM, deterministic tools, governance, feedback, memory, and stop
behavior. The deep-dive mechanism is **revision-bound behavior governance**:
the policy blocks dangerous actions independently of the model, feedback
changes the next turn, and writeback approvals bind to a current candidate
revision instead of a cross-object digest chain. The mechanism remains
independently testable after replacing the LLM with `ScriptedLLMV2`.

Route A extends that mechanism to the real filesystem without digest
identity: the same approval and revision predicates gate every byte written
to disk, a durable journal with ordinary byte comparison drives crash
recovery, and the path/object boundary (confinement, reparse refusal, strict
file typing, recheck-before-mutation) is deterministic code that never
depends on model cooperation.

Route B1 extends the same revision boundary to the validation plane:
candidate, diff, reference-profile, and validation records are keyed by
opaque IDs plus non-negative revisions, and evidence is accepted only when
its five control keys match the currently expected binding — the same
fail-closed comparison that gates writeback approvals, applied to
validation evidence instead of content digests.

Route B2 extends the boundary to the disclosure/provider/credential
plane: grants and per-request authorizations are keyed by opaque control
references, the ledger's scope, budget, expiry, replay, and binding
checks are deterministic code inside one transaction (never prompt
instructions), the provider call boundary holds the credential's raw
value only between the capability-gated `reveal` and the single
injectable transport call, and the atomic consume revalidates the full
binding plus the grant's current state before the one-shot transition —
every record, outcome, and error in the plane is a closed, static,
redacted shape that remains testable with a mock store, a fake
transport, and no network.

Route B3 extends the same fail-closed control plane to the local
operator surfaces: the `V2LocalShell` is a thin closed vocabulary over
the existing Route A services and B2 ports (never a new authority), the
CLI and the WebUI are both deterministic type/boundary checkers in
front of it — bounded typed arguments, allowlisted exact-set form
contracts, the literal `CONFIRM` gate, opaque-ID binding pre-checks,
preview-by-default with explicit `--apply`, and the fixed
HOST -> SESSION -> ORIGIN -> CSRF request order, where the SESSION
check is itself self-contained (the cookie must resolve to a session
registered in and still live at the WebUI's own session manager — a
forged or expired session value rejects before any form parsing or
domain call, and no session-taking authorization variant exists, so no
route handler can bypass the manager by passing an arbitrary session
object) — and every human-facing projection (CLI lines, HTML pages,
statuses, outcomes) is a bounded, escaped, non-revealing rendering of
control-plane facts.  The integration layer's mechanism is the same
revision-bound governance as Route A: a stale revision, an unknown run,
a mismatched candidate, or a polluted form rejects deterministically
before any mutation call, with zero writes and a closed reason — so
the whole surface remains independently testable offline with a
scripted LLM, an injected shell, and a loopback socket, with no
network, no Docker, and no third-party framework.

Route B4a extends the same revision-bound governance to the Docker
validation execution boundary.  The execution profile is an opaque
id+revision record whose isolation parameters are pinned fail-closed
at construction — a network-enabled, root-user, or docker-socket
profile is not representable — and the execution request is a closed
structured record that binds the B1 control plane (run, candidate,
and the candidate revision it cites) whose argv is a frozen
per-kind-grammar projection of its own control fields, so neither a
shell command string nor a request that names one candidate in its
binding and another in its argv is representable.  The service
enforces the fixed profile-binding -> control-plane binding ->
readiness -> one-call-no-retry order with closed, static, sanitized
outcomes (bounded, control-free excerpts), re-verifying every field
of the binding port's facts so a drifted or hostile lookup cannot
authorize a foreign or stale candidate.

Route B4b-01 extends the same boundary to a real container: the one
optional real execution adapter accepts only the closed request and
profile records and drives the operator's docker CLI through an
injectable command runner with a closed create -> drift-verify ->
start -> stop-on-timeout -> always-remove sequence, where the drift
verification re-checks the daemon-side configuration of the exact
created container before it starts, the attached run is bounded by
the profile's timeout and output ceilings, and every phase failure
maps to the closed sanitized result with the CLI/daemon error text
discarded.  Both real edges — the read-only probe and the execution
adapter — are injectable at the command runner, so even their
decision logic runs offline; the adapter is the only path to a real
container and composes only behind the B4a binding/readiness gates.
The whole boundary remains independently testable with the
deterministic fakes and (for the binding gate) a real v2 control
database: no network, no third-party package, and no v1 authority
module, and the real container path is exercised only by the opt-in
operator integration module that skips honestly when the daemon or
a token-named local image is unavailable.

## B4b-02C2 deployment boundary decision

The real v2 Harness is intentionally local-only in this alpha. The v2 WebUI binds to literal `127.0.0.1`, uses in-process sessions, and operates against a local workspace, local OS credential boundary, and local Docker/operator boundary. It is not a multi-user service and must not be exposed through a public bind or deployment configuration.

A future public service requires a separate product/security design for authentication, tenant/workspace isolation, cloud secret storage, TLS/reverse proxy, quotas, audit retention, and remote sandboxing. Changing the host bind is not an acceptable deployment migration. B4b-02C2 is intentionally not implemented.

## 9. v2 token-level streaming LLM boundary and TUI (2026-10-12)

The v2 LLM boundary gains a token-level streaming protocol and the operator
gains a streaming terminal UI, aligned with the Claude Code / pi experience
("方案 3"). All work stays on the v2 path; the frozen v1 `LLMAdapter`
one-call contract (`llm/base.py`, SPEC §4.2.1) is untouched.

**Streaming contract (llm/v2.py, loop/v2_engine.py).** `stream(request) ->
Iterator[str]` yields ordered text increments whose concatenation parses as
the JSON action object; `stream_events(request) -> Iterator[V2StreamEvent]`
is the typed variant that separates `reasoning` increments
(chain-of-thought, never part of the action text) from `content`
increments. The default behavior for a generate()-only LLM is
`stream_via_generate`: the full serialized action yielded as one chunk, so
`ScriptedLLMV2` stays drop-in compatible with zero changes.
`ScriptedStreamLLMV2` is the deterministic offline streaming mock
(fixed-size token chunks, optional scripted reasoning per turn).
`V2AgentLoop.run` resolves the boundary structurally: `stream_events` first,
then `stream`, then the default bridge; content increments are forwarded
through the optional `on_delta` callback, reasoning through `on_reasoning`,
and each turn's outcome (dispatch result, parse-failure feedback, or the
`LLM_CALL_FAILED` result) through `on_result`. With no callbacks attached
the loop's observable behavior is identical to the pre-streaming loop. An
unparseable aggregate feeds the existing feedback path (`V2ActionError`) —
not `LLM_CALL_FAILED`; only `Exception`-shaped failures map onto the
`LLM_CALL_FAILED` stop, so a `KeyboardInterrupt` raised from a callback
propagates and serves as the cancellation mechanism.

**Streaming TUI (vespercode/tui/).** `vespercode-v2 tui` opens a textual
app over one workspace: the task input is pre-filled, model output streams
token by token into the current turn's block (reasoning in a muted style),
and each turn closes the block with a bounded summary line — action name,
parameter summary (path, content char count; never full content in the
summary), and the dispatcher result, so guardrail denials are visible live.
`Ctrl+C` cancels the running turn via the callback-propagation path above;
`Ctrl+Q` quits. Writes stay staged in memory (the v2 approval-gated
writeback services remain the only mutation path); the final status line
reports the staged count. The package ships lazily: `v2_launch` (launch
spec + offline demo factory) and `v2_view_model` (pure presentation state)
are stdlib-only, while `v2_app` imports textual at module level and is
imported only when the command runs — the CLI core and every offline test
never require textual. The default LLM is the scripted streaming demo
(guardrail denial → feedback recovery → DONE), fully offline with no API
key.

**Real adapter (llm/v2_openai_adapter.py).** `V2OpenAICompatLLM` implements
the same boundary against any OpenAI-compatible `/chat/completions` SSE
endpoint. The transport is injectable (`V2OpenAIStreamTransport`: one POST
yielding byte chunks); the real transport lazily imports httpx with
`follow_redirects=False` and a fixed 60 s read timeout. The SSE reader
decodes lines incrementally, processes `data:` payloads only, and
terminates on the standard double-safeguard only — a chunk's
`finish_reason` or the `data: [DONE]` sentinel; the vendor-specific
`lastOne` flag is ignored. A stream whose bytes are exhausted without
either marker fails closed as `LLM_CALL_FAILED` — a truncated stream
never completes as normal output. A stream exceeding the closed 1 MiB
bound, a
non-200 status, or any transport exception maps onto the typed
`V2OpenAIAdapterError` with a static message (`CONFIG_MISSING` with setup
guidance, or `LLM_CALL_FAILED`); no secret, URL, header, or body fragment
reaches an exception text. LongCat's chain-of-thought travels on its own
typed channel: `reasoning_content` increments are yielded as
`V2StreamEvent("reasoning", ...)` and never mix into the action text; the
observed empty first `content` chunk emits nothing. The API key is read
once at construction from an injectable provider (default: the
`VESPERCODE_V2_BASE_URL`/`VESPERCODE_V2_MODEL`/`VESPERCODE_V2_API_KEY`
user-level environment variables), placed only into the Authorization
header, and never printed, logged, or stored; `vespercode-v2 tui --llm
openai [--base-url URL] [--model NAME]` never accepts a key on argv.
Explicit arguments override the environment; the environment overrides the
verified defaults (`https://api.longcat.chat/openai/v1`,
`LongCat-2.5-Preview`). The adapter imports no v1 contract type.

**Limitations.** The TUI is a local operator surface (loopback discipline
of B4b-02C2 applies); it stages writes in memory only and offers no
writeback path. The SSE reader assumes one complete JSON chunk per
`data:` line (the standard OpenAI-compatible wire format) and skips
malformed lines rather than failing the stream. `stream_via_generate`
round-trips the action through JSON, so a generate()-only LLM returning
non-JSON-serializable values now fails closed as `LLM_CALL_FAILED` instead
of reaching the dispatcher. Textual-backed tests skip honestly where
textual is not installed (the CI `unit-test` job installs no third-party
dependencies and runs the stdlib-only surface).
